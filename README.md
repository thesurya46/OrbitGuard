# OrbitGuard

**Real-Time Satellite Conjunction & Collision Risk Screening Dashboard**  
*Built for SUPERNOVA: Beyond the Cosmos by Team The Bit Busters (DRIEMS University)*

OrbitGuard is a modern space-safety dashboard that pulls live orbital data, propagates satellite trajectories forward in time, screens for close-approach events, and ranks collision risks in an intuitive, interactive UI.

### Key Features
- **SGP4 Orbital Propagation:** Propagates orbital paths forward in time using standard SGP4 models.
- **Precision Conjunction Screening:** Analyzes closest-approach distances over forecast windows.
- **Docking Proximity Filtering:** Automatically filters out near-zero (<0.5 km) approaches (such as docked ISS/Tiangong modules) to eliminate false-positive events.
- **Cross-Group Threat Screening:** Supports screening the space station complex against independent debris objects.
- **Composite Risk Scoring:** Blends miss distance and relative velocity to produce an actionable 0-100 risk index.
- **3D Orbit Visualization:** Visually represents satellite orbits and threat points interactively.

## Quick start

You'll need **Python 3.10+** and **Node.js 18+**. This project has network
dependencies (CelesTrak for live data, npm/pip for packages), so run these
steps somewhere with internet access.

### 1. Backend

```bash
cd backend
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# optional: (re)generate the bundled offline sample TLE set
python scripts/gen_sample_tles.py

# run the tests
pytest

# start the API
python run.py
```

The API is now live at `http://localhost:8000`. Interactive docs (Swagger
UI, auto-generated by FastAPI) are at `http://localhost:8000/docs` — handy
for demoing the pipeline to judges directly.

### 2. Frontend

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`. The Vite dev server proxies `/api/*` calls
to the backend automatically (see `vite.config.js`), so no extra config
is needed.

### 3. Run a screening

In the dashboard, click **Run Screening**. By default it uses the bundled
offline sample data (see below) so the demo works even without internet
or CelesTrak access. Uncheck "Use offline sample data" to pull and screen
live orbital objects instead.

## Offline sample data

`backend/data/sample_tles.txt` contains a real, publicly published example
ISS (ZARYA) TLE plus two synthetic "SIM-DEBRIS" objects generated by
`scripts/gen_sample_tles.py` — their orbital elements are nudged just
enough from the ISS's real elements that they reliably produce a flagged
close-approach when propagated, so the whole pipeline can be demoed with
zero network dependency (e.g. flaky venue wifi on hackathon day).

This is clearly separate from live-mode: uncheck "Use offline sample
data" in the dashboard (or pass `use_sample_data: false` to the API) to
pull real, current TLEs from CelesTrak and screen genuine tracked
objects instead.

## API reference

### `GET /api/health`
Returns service status and whether sample data is bundled.

### `GET /api/tles?group=stations&use_sample_data=false`
Returns the raw TLE records currently resolvable for a group.

### `POST /api/conjunctions/run`
Runs the full pipeline and returns ranked risk events.

```json
{
  "group": "stations",
  "threshold_km": 25,
  "window_hours": 72,
  "step_seconds": 60,
  "use_sample_data": true,
  "force_refresh": false
}
```

Response:

```json
{
  "generated_at_iso": "2026-08-12T10:00:00+00:00",
  "group": "stations",
  "objects_tracked": 3,
  "window_hours": 72,
  "threshold_km": 25,
  "events": [
    {
      "object_a": "ISS (ZARYA)",
      "object_b": "SIM-DEBRIS-1",
      "norad_id_a": "25544",
      "norad_id_b": "90001",
      "miss_distance_km": 4.82,
```

## The risk model, explained

Every flagged conjunction gets a single 0–100 risk score, so judges (and
future operators) don't have to mentally interpret raw kilometers and
km/s themselves:

```
risk = 70% × how deep into the "danger zone" the miss distance is
     + 30% × how fast the objects are closing (relative velocity)
```

Both components are normalized to `[0, 1]` before weighting — distance
proximity relative to your chosen safety threshold, and relative velocity
relative to a ~15 km/s reference (roughly the fastest closing speed for
crossing LEO orbits). Events are also tagged with an urgency label based
on time to closest approach: **Critical** (<6h), **High** (<24h),
**Moderate** (<48h), **Low** (beyond that).

The weights and reference velocity are constants in `backend/app/config.py`
— tune them for your specific risk appetite without touching any pipeline
logic.

## Known limitations / what a v2 would add

- **Conjunction screening is O(n² × timesteps)** — fine for the "stations"
  group or a few dozen objects, but would need a coarse spatial/altitude
  pre-filter before scaling to a full multi-thousand-object catalog.
- **The 3D orbit view is schematic**, not a literal replay of the
  SGP4-propagated path — the API currently returns the scored
  closest-approach summary rather than the full per-timestep trajectory.
  Extending `ConjunctionEvent` (or adding a dedicated endpoint) to include
  the position samples from `PropagatedObject` would make the 3D view
  physically exact.
- **No persistence layer** — every run is stateless. A production version
  would store historical runs so you can track how a conjunction's risk
  evolves as fresher TLE data comes in.
